**Prerequisite:** phase 2 (`specialAccessService`, and the `damage_evidence` scope)
**Gate:** `npm run gate`

### The design in one paragraph

`/field/ingest/{token}` keeps its path, its unauthenticated design, its single-use semantics and
its uniform `FIELD_TOKEN_INVALID` 404 (D17). Only the token's **storage** moves. Step 6.0 copies
every outstanding `cleaner_token` into `special_access` **before** anything reads from there. Each
site that mints a `cleanerToken` then also writes a `special_access` row carrying the **same**
token, in the same transaction; `getFieldContext` reads through `special_access`; the submit's burn
sets both `used_at` on the grant and `token_expires_at = now` on the item.
`incident_items.cleaner_token` and `token_expires_at` stay **written** as a mirror so this can be
reverted by re-pointing one read (D18) — they are dropped in a later feature, not this one.

**Step order is load-bearing.** 6.0 (backfill) must land before 6.3 (read move), or every
outstanding field link dies at 6.3. 6.1–6.2 keep new grants mirrored; 6.4 keeps the mirror burned.
A partial phase that runs 6.3 without 6.0 is the one combination that loses data.

### Step 6.0 — Backfill outstanding field tokens into `special_access`

**Touch.** `drizzle/0016_*.sql` (generated), `drizzle/meta/*` (generated)

**Do.** The read move in 6.3 finds the item through `special_access`. Rows minted before this
feature have no grant there, so without this step every link a host has already sent stops working
the moment 6.3 commits.

Generate an empty migration and paste the backfill into it:

```bash
npx drizzle-kit generate --custom --name=backfill_field_grants
```

That writes `drizzle/0016_backfill_field_grants.sql` (drizzle-kit owns the name; do not rename it)
and appends an entry to `drizzle/meta/_journal.json`. Confirm both before pasting:

- exactly one new `.sql` appears, and its index is `16`
- `_journal.json` gained one entry with `"tag": "0016_backfill_field_grants"`

Then paste exactly this into that file:

```sql
INSERT INTO "special_access" (
  "access_id", "scope", "apartment_id", "reservation_id", "incident_item_id", "expires_at", "created_at"
)
SELECT
  ii."cleaner_token",
  'damage_evidence',
  r."apartment_id",
  r."id",
  ii."id",
  ii."token_expires_at",
  now()
FROM "incident_items" ii
JOIN "incidents" i ON i."id" = ii."incident_id"
JOIN "reservations" r ON r."id" = i."reservation_id"
WHERE ii."token_expires_at" > now()
  AND NOT EXISTS (
    SELECT 1 FROM "special_access" sa WHERE sa."access_id" = ii."cleaner_token"
  );
```

Four things about this statement, each deliberate:

- **`id` is omitted**, so `gen_random_uuid()` (the column default) supplies it. Do not add an `id`
  expression.
- **`WHERE token_expires_at > now()`** copies only the links that are still live. An expired or
  already-burned item's token resolves to `null` either way — with a grant row whose `expires_at`
  is in the past, or with no row at all — so copying dead rows would add data that can never be
  read. A live row's `used_at` is correctly `NULL`, which is why `used_at` is omitted.
- **`NOT EXISTS`** makes the statement idempotent, so a re-run after a partial failure is safe
  rather than a UNIQUE violation on `access_id`.
- **`created_by` is omitted (NULL).** Legacy tokens predate the grant table and have no recorded
  minter; the column is nullable and its FK is `SET NULL`, so NULL is the honest value. Do not
  invent one.

`reservation_id` is stored even though the scope is `damage_evidence`: the CHECK requires
`incident_item_id`, and `reservation_id` is the subject's reservation, which 6.1's helper also
stores. Keeping the two paths identical is what lets 6.3's join be the only reader.

**Accept.**

- `ls drizzle/0016_*.sql` → one file
- `node -e "const j=require('./drizzle/meta/_journal.json');console.log(j.entries.at(-1).tag)"` → `0016_backfill_field_grants`
- **Against a copy of the data, not production:** `npm run db:migrate`, then
  `psql "$DATABASE_URL" -c "select count(*) from special_access where scope='damage_evidence'"` →
  a count `> 0` on any database that has live field links, and equal to
  `select count(*) from incident_items where token_expires_at > now()`
- Re-running `npm run db:migrate` is a no-op (the migration is recorded), and re-running the
  `INSERT` by hand inserts **0** rows — the `NOT EXISTS` guard

**Verify.** `npm run gate`

> **Halt and report** if the copy's counts do not match, or if the migration cannot be run against
> a copy first. This is the only step in the feature that writes to data it did not create, and a
> wrong count here is silent — the field links simply stop working.

### Step 6.1 — A helper that mints the paired grant

**Touch.** `src/modules/incidents/incidents.service.ts` (edit)
**Do.** Add near `makeToken`:

```ts
/**
 * The `special_access` twin of a field token (D18).
 *
 * The token is the SAME string as `incident_items.cleaner_token`, so the two
 * tables describe one credential during the migration window: `getFieldContext`
 * reads the grant, and the item column stays the revert path. Written inside the
 * caller's transaction so a grant can never exist for an item that failed to
 * insert, or vice versa.
 *
 * `expiresAt` is passed rather than recomputed, so the grant's window and the
 * item's `token_expires_at` cannot drift by a few milliseconds.
 *
 * `apartmentId` is passed rather than joined here: every caller already holds the
 * reservation, and a second query per mint would be paid on the hot create path.
 */
const insertFieldGrant = async (
  tx: Variables["db"],
  params: {
    token: string;
    expiresAt: Date;
    apartmentId: string;
    reservationId: string;
    incidentItemId: string;
    createdBy: string | null;
  },
) => {
  await tx.insert(specialAccess).values({
    accessId: params.token,
    scope: "damage_evidence",
    apartmentId: params.apartmentId,
    reservationId: params.reservationId,
    incidentItemId: params.incidentItemId,
    expiresAt: params.expiresAt,
    createdBy: params.createdBy,
  });
};
```

and add `specialAccess` to the `@/db` import at the top of the file (it is already importing from
`@/db`; add the symbol to that list, do not add a second import).

**Accept.** `npx tsc --noEmit` → exit 0. (`eslint` reports the unused helper as a *warning*, and

#### 6.2c — `reissueToken`

`reissueToken` today is a bare `db.update(...)` with **no transaction**, and the grant write must be
atomic with it. Restructure it to a transaction, and delete the superseded grant before inserting
the new one — because `access_id` is UNIQUE and the old token must stop working:

```ts
  async reissueToken(
    db: Variables["db"],
    incidentId: string,
    itemId: string,
    context: { apartmentId: string; reservationId: string; createdBy: string | null },
  ): Promise<IncidentItemWithToken | null> {
    const token = makeToken();
    const expiresAt = new Date(Date.now() + TOKEN_TTL_MS);

    const updated = await db.transaction(async (tx) => {
      const [row] = await tx
        .update(incidentItems)
        .set({ cleanerToken: token, tokenExpiresAt: expiresAt, updatedAt: new Date() })
        .where(
          and(
            eq(incidentItems.id, itemId),
            eq(incidentItems.incidentId, incidentId),
            eq(incidentItems.status, "link_generated"),
          ),
        )
        .returning();

      if (!row) return null;

      // Replace, never add a second live grant for this item: the superseded
      // token must stop working in the same write that mints the new one, which
      // is the guarantee `cleaner_token`'s UNIQUE column gives today.
      await tx.delete(specialAccess).where(eq(specialAccess.incidentItemId, itemId));

      await insertFieldGrant(tx, {
        token,
        expiresAt,
        apartmentId: context.apartmentId,
        reservationId: context.reservationId,
        incidentItemId: itemId,
        createdBy: context.createdBy,
      });

      return row;
    });

    if (!updated) return null;

    return this.getItemWithToken(db, incidentId, itemId);
  },
```

`reservationId` is passed in rather than derived here because `incident_items` has no
`reservation_id` — it reaches one only through its incident, which the caller has already resolved.

The handler needs that reservation, which `requireItem` does not currently return. `requireItem` is
built on `resolveOwnedIncident`, which **already loads** the reservation for its ownership check and
then drops it; return it instead of adding a query:

```ts
async function resolveOwnedIncident(c: any, id: string) {
  // ...unchanged up to and including the assertApartmentOwnership call...

  return { db, incident, reservation };
}
```

`requireItem` then returns `{ db, incident, item, reservation }`, and
`reissueItemTokenRoute` calls:

```ts
  const { db, reservation } = await requireItem(c, id, itemId);
  const user = c.get("user");

  if (!user) {
    throw incidentErrors.unauthenticated();
  }

  // ...unchanged activeCount guard...

  const reissued = await incidentsService.reissueToken(db, id, itemId, {
    apartmentId: reservation.apartmentId,
    reservationId: reservation.id,
    createdBy: user.id,
  });
```

> **`resolveOwnedIncident` has five callers**, and widening its return value is compatible with all
> of them — the four that destructure `{ db }` or `{ db, incident }` simply ignore the new key. No
> edit is needed at those four sites.

> **This breaks two tests, and the change to `resolveOwnedIncident` is why they are not optional.**
> In `incidents.service.test.ts`, the `reissueDb` stub (around line 833) provides `update` and
> `query` but **no `transaction`**, and the two `reissueToken` cases (around lines 862 and 886) call
> it with three arguments. Both must be updated: give the stub a
> `transaction: (fn) => fn(chain)` (the `fakeDb` helper in the same file already shows the idiom),
> and pass the fourth argument. This is a real test edit, not a plan error — `reissueToken`'s
> signature is changing on purpose.

### Step 6.3 — Read the grant instead of the column

**Touch.** `src/modules/incidents/incidents.service.ts` (edit)

**Do.** In `getFieldContext`, change the `where` and add the grant join, so the row is found through
`special_access` rather than through `incidentItems.cleanerToken`:

```ts
    const [row] = await db
      .select({
        itemId: incidentItems.id,
        itemType: incidentItems.type,
        itemStatus: incidentItems.status,
        tokenExpiresAt: specialAccess.expiresAt,
        incidentId: incidents.id,
        apartmentId: apartments.id,

        checkOutDatetime: reservations.checkOutDatetime,
        alternativeCheckOutDatetime: reservations.alternativeCheckOutDatetime,

      .from(specialAccess)
      .innerJoin(incidentItems, eq(specialAccess.incidentItemId, incidentItems.id))
      .innerJoin(incidents, eq(incidentItems.incidentId, incidents.id))
      .innerJoin(reservations, eq(incidents.reservationId, reservations.id))
      .innerJoin(apartments, eq(reservations.apartmentId, apartments.id))
      .where(
        and(
          eq(specialAccess.accessId, token),
          eq(specialAccess.scope, "damage_evidence"),
          isNull(specialAccess.revokedAt),
          isNull(specialAccess.usedAt),
        ),
      )
      .limit(1);
```

The four predicates replace the old code's one `where` plus its expiry check:
`isNull(revokedAt)` is new capability the column could not express (a host can now cut a field link
off), `isNull(usedAt)` is the single-use rule the old `tokenExpiresAt <= now` check implemented by
burning the timestamp, and the `scope` filter keeps an `inspection_proof` token from opening the
field surface.

The `tokenExpiresAt <= Date.now()` check immediately below **stays exactly as it is** — `expiresAt`
is now the grant's, and the comparison reads the same field name. Do not delete it: without it an
expired-but-unused grant would still resolve, which is precisely the case the backfill's
`WHERE token_expires_at > now()` also excludes.

### Step 6.4 — Burn the grant at submit

**Touch.** `src/modules/incidents/incidents.service.ts` (edit)

**Do.** The burn lives in `recomputeItemStatus(tx, itemId)` (around line 284), which sets
`...(status === "link_generated" ? {} : { tokenExpiresAt: new Date() })`. That helper has **three**
callers — `submitFieldEvidence`, `attachEvidence` and `deleteEvidence` — so putting the grant burn
there covers the field submit *and* the two host paths that also consume an item's link, which is
what keeps the two tables in step.

Replace that spread with an explicit branch, so the grant is burned **exactly when** the column is
and the two cannot diverge:

```ts
  await tx
    .update(incidentItems)
    .set({
      status,
      // The link has no job left once anything is attached, so it dies with the
      // first attach (D11). An item wiped back to `link_generated` keeps the
      // burned token and must have its link reissued.
      ...(status === "link_generated" ? {} : { tokenExpiresAt: new Date() }),
      updatedAt: new Date(),
    })
    .where(eq(incidentItems.id, itemId));

  // The grant is burned with the column, and only with it (D18): an item wiped
  // back to `link_generated` keeps a usable link on BOTH sides, so reissuing
  // replaces a dead grant rather than colliding with a live one.
  if (status !== "link_generated") {
    await tx
      .update(specialAccess)
      .set({ usedAt: new Date() })
      .where(eq(specialAccess.incidentItemId, itemId));
  }
```

Item column and grant are now burned together, so a replay fails on **either** read — which is what
makes the migration revertable: if `getFieldContext` is pointed back at the column, the column was
still being burned the whole time.

> The `status !== "link_generated"` guard is not tidiness. `deleteEvidence` can wipe an item back to
> `link_generated` after its token was burned; the column keeps the old burned timestamp in that
> branch, and the grant must keep its `usedAt` too, or the two tables disagree about whether the
> link is dead.

**Accept.** `npx vitest run src/modules/incidents` → all pass, including the existing "burns the
token in the same write that consumes it" case (`incidents.service.test.ts`, around line 434) with
no test edited — that case asserts on the `update` ops it recorded, and the new grant update is an
additional op rather than a change to the one it checks. If it fails on op *ordering*, that is the
positional `fakeTx` queue and the new op must be added to the fixture's `mutates` plan; report it
rather than reordering the code to suit the stub.

**Verify.** `npm run gate`

### Step 6.5 — Prove the mirror cannot drift

**Touch.** `src/modules/incidents/incidents.service.test.ts` (edit)

**Do.** The existing field tests prove behaviour, but they would still pass if the grant write were

```ts
describe("field grants mirror the item token — D18", () => {
  it("inserts a damage_evidence grant carrying the same token it writes on the item", async () => {
    const inserted: Array<Record<string, unknown>> = [];
    let lastValues: unknown;

    // A tx stub that records every insert payload and, like Postgres, echoes the
    // STORED row back from `returning()` — so `created.cleanerToken` is the token
    // that was actually written. Answering a bare fixture here instead would let
    // the grant and the item carry different tokens and still pass.
    const tx: any = {
      select: () => tx,
      from: () => tx,
      innerJoin: () => tx,
      where: () => tx,
      limit: () => tx,
      orderBy: () => tx,
      insert: () => tx,
      values: (v: unknown) => {
        inserted.push(v as Record<string, unknown>);
        lastValues = v;
        return tx;
      },
      returning: () =>
        Promise.resolve(
          Array.isArray(lastValues)
            ? (lastValues as object[]).map((row) => ({ id: ITEM_ID, ...row }))
            : [{ id: ITEM_ID, ...(lastValues as object) }],
        ),
      update: () => tx,
      set: () => tx,
      delete: () => tx,
      // Every plain `await` in `addItem` (the duplicate check, the asset lookup,
      // the two readiness updates) resolves empty, which is what makes the happy
      // path run to the end.
      then: (res: any, rej: any) => Promise.resolve([]).then(res, rej),
    };

    const db: any = { ...tx, transaction: (fn: any) => fn(tx) };

    await incidentsService.addItem(
      db,
      INCIDENT_ID,
      { assetId: ASSET_ID, type: "damage" },
      { apartmentId: APARTMENT_ID, createdBy: null },
    );

    const grant = inserted.find((row) => row.scope === "damage_evidence");
    const item = inserted.find((row) => "cleanerToken" in row);

    expect(grant).toBeDefined();
    expect(item).toBeDefined();

    // and the item one is the one nothing reads any more.
    expect(grant!.accessId).toBe(item!.cleanerToken);
    expect(grant!.incidentItemId).toBe(ITEM_ID);
  });
```

## Phase 6 invariants

- [ ] Step 6.0 ran against a copy of the data before 6.3 landed, and its copied-row count equals
      the live-token count
- [ ] All three mint sites mirror; a grep for `insertFieldGrant` finds the definition plus three calls
- [ ] `reissueToken` deletes the superseded grant inside a transaction, so the old token stops
      working — the same guarantee `cleaner_token` gives today
- [ ] `getFieldContext` filters on `scope`, `revoked_at` and `used_at`, and **keeps** the
      `tokenExpiresAt` comparison
- [ ] The submit burns the grant and the item column together, and neither is burned while the
      status is still `link_generated`
- [ ] `cleaner_token` and `token_expires_at` are still written — not dropped (D18)
- [ ] No field-surface payload, path or status changed: `incidents.field.test.ts` passes unmodified
- [ ] `FIELD_TOKEN_INVALID` remains the only failure code on that surface — a dead grant is a 404,
      not one of the new 403s (D17)
- [ ] Reverting the read move is a one-line change: point `getFieldContext` back at
      `incidentItems.cleanerToken` and 6.0's rows become inert, because the column was burned and
      mirrored the whole time
