**Prerequisite:** phase 3 (the guard resolves through `specialAccessService.resolveByToken` and
throws `specialAccessErrors`, both created in phase 2 and exercised in phase 3)
**Gate:** `npm run gate`

---

### Step 4.1 — The guard

**Touch.** `src/middleware/specialAccessGuard.ts` (create)

**Do.** The full file is 130 lines and is reproduced in
[`reference/specialAccessGuard.ts.txt`](./reference/specialAccessGuard.ts.txt). Copy it verbatim into
`src/middleware/specialAccessGuard.ts`.

Its contract, so the executor can confirm the right file landed:

- Exports `AccessBind` — a closed union of `reservationParam`, `apartmentParam`, `reservationBody`.
- Exports `specialAccessGuard({ scope, bind, roles })`, a `createMiddleware<App>`.
- **No `accessId`** → `await authGuard(c, …)` wrapping `await rolesGuard(roles)(c, next)`. The same
  two middlewares, called rather than reimplemented, so the session path cannot drift.
- **`accessId` present** → `resolveByToken`; `null` throws `SPECIAL_ACCESS_INVALID`; a scope
  mismatch or a target mismatch throws `SPECIAL_ACCESS_SCOPE_MISMATCH`; then
  `resolveApartmentOwner`, whose `null` also throws `SPECIAL_ACCESS_INVALID`; then `c.set("user", owner)`.
- **Ordering is load-bearing:** the token is validated before the target is resolved, and
  `resolveApartmentOwner` is not reached for a bad token. This is the step whose tests assert it.
- `targetMatches` reads path params directly and, for a body-bound target, `c.req.raw.clone().json()`
  — because `createRoute`'s validators run *after* `middleware`. An unparseable body returns `true`
  so the validator that follows produces the 400, not a misleading 403.

**Accept.** `npx tsc --noEmit` → exit 0.

**Verify.** `npm run gate`

### Step 4.2 — Test the guard

Tests are never deferred to review. This phase is the one where a wrong choice is a security hole,
so its suite is the feature's most important.

**Touch.** `src/middleware/specialAccessGuard.test.ts` (create)

**Do.** The full file is 336 lines and is reproduced in
[`reference/specialAccessGuard.test.ts.txt`](./reference/specialAccessGuard.test.ts.txt). Copy it verbatim.

It builds a **real** `OpenAPIHono` app per case rather than stubbing the guard's caller, because the
guard's whole job is ordering and ordering is only observable through Hono's actual dispatch. The
two cases that must never be weakened:

- `"does NOT fall back to the session when the token is bad"` — a bad `accessId` **and** a valid
  `Authorization` header still 403s, and `usersService.getByAuthId` is never called. This is D6.
- `"validates the token BEFORE reading the target"` — `resolveApartmentOwner` is never called for a
  bad token. This is D9, and it is what makes a 403 safe rather than an existence oracle.

**Accept.** `npx vitest run src/middleware/specialAccessGuard.test.ts` → **14** tests passing, 0 failing; `npm run gate` → **779** tests passing (765 after phase 3, + 14)

**Verify.** `npm run gate`

## Phase 4 invariants

- [ ] `specialAccessGuard` contains none of the substrings `authGuard`, `rolesGuard`,
      `apartmentGuard` — it must not trip, nor satisfy, `check-contracts.ts`'s guard detection; the
      routes in phase 5 declare their statuses by hand
- [ ] The no-token path calls the real `authGuard` and `rolesGuard`, not a copy of their logic
- [ ] A bad token never reaches `resolveApartmentOwner`
- [ ] A request with both a bad token and a valid session is still refused
- [ ] The guard never constructs an error envelope — it throws
