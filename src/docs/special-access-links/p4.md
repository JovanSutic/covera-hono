# Phase 4 — Let a link-holder submit the guide's proofs

Prerequisite: phase 2 complete. Gate: `npm run gate`, plus `npm run gate:openapi` for step 4.1.

This closes B5 and use case 2 for page 2 (`/inspection-guide/:apartmentId/:reservationId`): the
link-holder can upload and confirm the inspection photos and record that the proofs are done — the
frontend's three-call submit chain, in order.

This is the phase the source docs get wrong, in two places, and both are load-bearing:

- `specialAccessGuard`'s session branch calls `authGuard` + `rolesGuard` **only**. On the two photo
  routes the ownership check comes *solely* from `apartmentGuard(false)`, and neither handler
  asserts ownership. Swapping the guard without step 4.1 would let any signed-in host mint upload
  tokens and confirm photos for **any** apartment.
- `check-contracts.ts` finds guards **by name**. Swapping makes it stop requiring 401 and 403 on
  the swapped routes, so the gate would silently get weaker exactly where the diff is riskiest.
  Step 4.3 extends it — deliberately last, once every `specialAccessGuard` route declares its
  statuses.

Decisions in play: D9, D10, D15, D16, D17, D18.

**Do (a) — the narrowed schema.** Append to `reservations.schema.ts`, after `UpdateReservationSchema`:

```ts
/**
 * What an access link may change about a reservation: exactly the two fields the
 * inspection guide's submit chain sends when it finishes — nothing else.
 *
 * `UpdateReservationSchema` is `CreateReservationSchema.partial()`, so it would
 * also let a link-holder move `checkInDatetime` / `checkOutDatetime`, a wider
 * capability than "record that the proofs are done" and one that can collide with
 * another stay.
 *
 * `strictObject`, not `object`: a plain object STRIPS unknown keys, so
 * `safeParse` would succeed on a body carrying the dates and the move would slip
 * through. Strict is what makes the rule enforceable.
 *
 * `status` is the literal `COVERED`, not the status enum: DISPUTED, RESOLVED and
 * CLOSED are resolution states that belong to the host and the guest, not to
 * whoever is holding a photo link.
 */
export const ProofCompletionSchema = z
  .strictObject({
    hasPhotoProof: z.boolean().optional(),
    status: z.literal("COVERED").optional(),
  })
  .openapi("ProofCompletion");
```

```ts
app.openapi(updateReservationRoute, async (c) => {
  const db = c.get("db");
  const { id } = c.req.valid("param");
  const body = c.req.valid("json");

  // D17/D18: a token request is narrowed to the two fields the guide's submit
  // chain sends. The query is read here rather than through `c.req.valid`,
  // because it is the GUARD's transport rather than this route's declared
  // contract — the guard has already validated the token and set `user` to the
  // apartment's owner, so there is nothing left to check but the body.
  //
  // The failure is a 400 with the envelope's `details[]`, not a second 403: the
  // credential is valid and the request is malformed, which is what a validator
  // would have produced had JSON Schema been able to express the rule.
  if (c.req.query("accessId")) {
    const completion = ProofCompletionSchema.safeParse(body);

    if (!completion.success) {
      throw new BadRequestException({
        code: "VALIDATION_ERROR",
        message:
          "An access link may only record that the proofs are done. It can set " +
          "hasPhotoProof and status (COVERED), and nothing else.",
        details: completion.error.issues.map((issue) => ({
          field: issue.path.join(".") || "body",
          message: issue.message,
        })),
        meta: { origin: "DOMAIN", via: "access-link" },
      });
    }
  }

  const updatedReservation = await reservationsService.update(db, id, body);

  if (!updatedReservation) {
    throw reservationErrors.notFound({ id });
  }

  return c.json(updatedReservation, 200);
});
```
