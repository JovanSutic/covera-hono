# Phase 5 — Introspection and listing

Prerequisite: phase 2 complete (this phase imports `AccessIdQuerySchema`'s sibling
`AccessIdParamSchema`, which already exists, and relies on the scheme being declared). Gate:
`npm run gate`, plus `npm run gate:openapi`.

Two new operations on the resource that already exists. Neither changes any existing route.

- **Introspection** is what lets the frontend validate a link **before** it renders, for a visitor
  with no session. Without it a route guard has only two options, both worse: test that the
  parameter is *present* (which proves nothing), or fire a real read and interpret its status
  (which inherits B3's 500).
- **Listing** is what lets a host see and revoke a link after the session that minted it ended.
  Today the only operations are create and revoke, so `revokedAt` and `usedAt` are stored but
  unreachable.

Decisions in play: D21, D22, D23, D24, D25, D26, D28, D29.

## Step 5.1 — The three shapes

**Touch:** `src/modules/special_access/special_access.schema.ts`

**Do:** Append after `AccessIdParamSchema`:

```ts
/**
 * The introspection payload, deliberately NARROWER than `SpecialAccess` (D21).
 *
 * The route is anonymous — the `accessId` in the path is the caller's own
 * credential — so it must not return more than the link already grants. The row
 * `id`, `revokedAt`, `usedAt` and `createdAt` are internal or management data
 * with no use to a link-holder, so they are not in this shape at all.
 */
export const SpecialAccessIntrospectionSchema = z
  .object({
    scope: AccessScopeSchema,
    apartmentId: z.uuid(),
    reservationId: z.uuid().nullable(),
    incidentItemId: z.uuid().nullable(),
    expiresAt: z.string().datetime(),
  })
  .openapi("SpecialAccessIntrospection");

/**
 * The list filter. `reservationId` is REQUIRED rather than optional (D24): the
 * only consumer is the reservation page, and an apartment-wide list would need
 * its own ownership resolution for no caller that exists.
 */
export const ListSpecialAccessQuerySchema = z.object({
  reservationId: z.uuid().openapi({
    param: { name: "reservationId", in: "query" },
    description: "The reservation whose access links should be listed.",
    example: "987e6543-e21b-12d3-a456-426614174000",
  }),
});

/**
 * The host's list of links (D25, D26).
 *
 * It reuses `SpecialAccessSchema` rather than declaring a near-copy — so it DOES
 * carry `accessId`, which is a deliberate relaxation of the rule stated on
 * `createSpecialAccessRoute` ("the response carries `accessId` — the only payload
 * that does"). It is safe only because this route is host-authorized against the
 * grant's own apartment, and it is required: without `accessId` the host cannot
 * rebuild the shareable URL, which is the whole point of the list.
 *
 * Revoked grants are included for the same reason: a host needs to see that a
 * link is dead, and needs the id to say which.
 */
export const SpecialAccessListSchema = z
  .array(SpecialAccessSchema)
  .openapi("SpecialAccessList");
```

## Step 5.2 — The lookup the list needs

**Touch:** `src/modules/special_access/special_access.service.ts`

**Do (a) — the import.** Change `import { and, eq, isNull } from "drizzle-orm";` to:

```ts

```

**Do (b) — the method.** Add to `specialAccessService`, after `findByToken`:

```ts
  /**
   * Every grant ever minted for one reservation, newest first, INCLUDING revoked
   * and expired ones.
   *
   * Revoked grants are returned on purpose: the host's question is "is the link I
   * sent still alive?", and a row that silently vanished cannot answer it. Telling
   * a dead link from a live one is the caller's job, from `revokedAt` and
   * `expiresAt`.
   *
   * This is the MANAGEMENT view, not a redemption — `findByToken`'s stance, not
   * `resolveByToken`'s — because the caller is a host looking at their own links.
   */
  async listByReservation(
    db: Variables["db"],
    reservationId: string,
  ): Promise<SpecialAccess[]> {
    const rows = await db
      .select()
      .from(specialAccess)
      .where(eq(specialAccess.reservationId, reservationId))
      .orderBy(desc(specialAccess.createdAt));

    return rows as SpecialAccess[];
  },
```

```ts
/**
 * What is behind this link, for a caller who has nothing else (D21, D22).
 *
 * ANONYMOUS BY DESIGN: the `accessId` in the path is the credential, exactly as
 * the token in `/field/ingest/{token}` is. Requiring a bearer session would make
 * this useless to the one caller it exists for — a frontend route guard that
 * validates a link before the page renders, for a visitor who has no account.
 *
 * Resolution is `resolveByToken`, the REDEMPTION lookup, which collapses unknown,
 * expired and revoked to `null`. All three therefore become one 403
 * `SPECIAL_ACCESS_INVALID`, so the route is not an oracle for which links once
 * existed. `findByToken` — what revoke uses — would return revoked grants.
 *
 * A spent (`usedAt`) grant still answers 200 today; that is recorded as D23, and
 * the frontend never introspects the scope where it can happen.
 */
export const getSpecialAccessRoute = createRoute({
  method: "get",
  path: "/{accessId}",
  tags: ["Special access"],
  middleware: [] as const,
  request: {
    params: AccessIdParamSchema,
  },
  responses: {
    200: {
      description: "The grant behind this link",
      content: {
        "application/json": {
          schema: SpecialAccessIntrospectionSchema,
        },
      },
    },
    ...specialAccessIntrospectionErrors,
  },
});

/**
 * The links minted for one reservation (D24, D25).
 *
 * Session-only and host-authorized against the grant's OWN apartment, copying
 * `revokeSpecialAccessRoute`'s pattern rather than inventing one — which is what
 * stops a host listing another host's links.
 */
export const listSpecialAccessRoute = createRoute({
  method: "get",
  path: "/",
  tags: ["Special access"],
  middleware: [authGuard, rolesGuard(["admin", "host"])] as const,
  request: {
    query: ListSpecialAccessQuerySchema,
  },
  responses: {
    200: {
      description: "The access links minted for this reservation",
      content: {
        "application/json": {
          schema: SpecialAccessListSchema,
        },
      },
    },
    ...listSpecialAccessErrors,
  },
});
```

```ts
app.openapi(getSpecialAccessRoute, async (c) => {
  const db = c.get("db");
  const { accessId } = c.req.valid("param");

  const grant = await specialAccessService.resolveByToken(db, accessId);

  if (!grant) {
    // One code for unknown, expired and revoked alike — asking which one it was
    // is asking for an existence oracle.
    throw specialAccessErrors.invalid({});
  }

  // Built field by field rather than spreading the row: `SpecialAccessSchema`
  // includes `id`, `revokedAt`, `usedAt` and `createdAt`, and an anonymous caller
  // must not receive them (D21). A spread here would silently widen the payload
  // the day a column is added.
  return c.json(
    {
      scope: grant.scope,
      apartmentId: grant.apartmentId,
      reservationId: grant.reservationId,
      incidentItemId: grant.incidentItemId,
      expiresAt: new Date(grant.expiresAt).toISOString(),
    },
    200,
  );
});

app.openapi(listSpecialAccessRoute, async (c) => {
  const db = c.get("db");
  const { reservationId } = c.req.valid("query");
  const user = c.get("user");

  if (!user) {
    throw incidentErrors.unauthenticated();
  }

  // Ownership is asserted against the SUBJECT's apartment, exactly as create and
  // revoke do. Resolving through the reservation is what makes this host-scoped:
  // the apartment comes from the reservation, never from the caller.
  const subject = await specialAccessService.resolveSubjectApartment(db, {
    reservationId,
  });

  if (!subject) {
    throw reservationErrors.notFound({ id: reservationId });
  }

  await assertApartmentOwnership(db, subject.apartmentId, {
    userId: user.id,
    role: user.role,
    allowAdmin: true,
  });

  const grants = await specialAccessService.listByReservation(db, reservationId);

  return c.json(grants, 200);
});
```
