# Special access links — decisions

Every choice the executor would otherwise make mid-flight. Approve the table in one pass, or
edit it in place; do not leave a row in `OPEN`.

**Status values:** `APPROVED` · `OPEN` (blocks execution) · `REJECTED` (kept for the record)

Facts below were verified against the codebase and the deployed API on **2026-11-26**
(branch `feature/53_special-access-fixes`, HEAD `c1a166d`, baseline `npm run gate` green:
783 tests, 49 routes).

## Decisions

| ID | Decision | Rationale | Status |
| --- | --- | --- | --- |
| D1 | The plan covers `covera-hono` only, plus one final docs phase that writes the frontend hand-off contract (the probe table and the `api:generate` / `gate` steps `covera` must run). | Operator's answer. The two repos have separate gates and separate habits; a single plan that executed both would have two acceptance criteria per step and no honest `Verify` line. | APPROVED |
| D2 | B0 is one phase whose durable half is code (a `Migrate database` step in `.github/workflows/deploy.yml` **before** `wrangler deploy`) and whose operational half is an operator action (`npm run db:migrate` against production) proved by re-probing. The plan never reads or handles the credential. | Operator's answer. The deploy step is the item that stops the *next* migration from repeating this outage; the plan cannot and must not carry a production `DATABASE_URL`. | APPROVED |
| D3 | First step of B0's phase is a **reproduction** of the outage (`GET /field/ingest/bogustoken` → 500), the last is a probe of the same URL → 404. | Re-verified 2026-11-26: `/users` 401, `/reservations/{id}?accessId=` 401, `?accessId=deadbeef` 500, `/field/ingest/bogustoken` 500, `GET /special-access/x` 404. A phase whose fix is ops needs a probe, not a test — this is the only honest acceptance criterion. | APPROVED |
| D4 | The migration phase is **first** and every later phase's contract is unaffected by it. | Domain logic is what the other phases change, and none of it is observable in production until the table exists. Landing it first also means the post-B0 probe answers the B3 question (403 vs still-500) before any code is written for B3. | APPROVED |
| D5 | B3 gets **no phase**. If the post-B0 probe returns 403 `SPECIAL_ACCESS_INVALID`, B3 closes for free (the guard's logic is already correct and its 14-test suite is green). If it stays 500, `p1.md`'s halt condition fires and the code-level checklist runs as new work. | The guard resolves an unknown token to `specialAccessErrors.invalid({})` → 403 today; migration `0015` creates the relation the query needs. Planning code for a failure whose documented cause is a missing table is how a plan invents work. | APPROVED |
| D6 | `?accessId=` becomes a declared optional **query** parameter on all **thirteen** token-enabled routes (six existing + four claim routes + three submit routes), through one shared `AccessIdQuerySchema` exported from `special_access.schema.ts`. | The frontend's `accessQuery = (accessId) => ({ accessId }) as never` exists only because the generated type says `query?: never`. One spelling, one place to change it. Adding to an existing `request.query` (apartment_shots, and any future one) means spreading the object, never replacing it. Count verified against the built document on 2026-11-26. | APPROVED |
| D7 | `securitySchemes.specialAccess` is registered as `{ type: "apiKey", in: "query", name: "accessId" }`; **no** route carries a `security: [...]` array. | In OpenAPI a route-level `security` array means "required", which would tell a generator that every guarded route needs a token — the opposite of the guard's either-or semantics. The scheme is a declaration; the description states the semantics OpenAPI 3.0 cannot express. | APPROVED |
| D8 | `SPECIAL_ACCESS_INVALID` and `SPECIAL_ACCESS_SCOPE_MISMATCH` are added to `getReservationByIdErrors` (one edit, both reservation reads) and to the bundles of the four newly-token-enabled read routes. The existing three token-enabled reads already declare them and are not touched. | Both reservation reads mount `specialAccessGuard` and can produce both codes; the bundle is shared, so it is a two-line edit fixing two routes. The others already carry them — verified in their contract files. | APPROVED |
| D9 | `scripts/check-contracts.ts` **is** extended, in the same phase as the first guard swap, to recognise `specialAccessGuard` in `middleware` and require a 403 on those routes. | Not optional: the checker finds guards by name (`authGuard`, `rolesGuard`, `apartmentGuard`). Phase 4 replaces `[authGuard, rolesGuard, apartmentGuard(false)]` with `[specialAccessGuard(...)]`, which would make the checker stop requiring **both** 401 and 403 on those routes — the gate would get *weaker* exactly where the diff is riskiest. The extension restores and strengthens it. Rejected alternative: leaving the checker alone and treating this as a one-off contract fix — it silently loses coverage on every route the swap touches. | APPROVED |
| D10 | Extending the checker must require a 403 for the **existing** `specialAccessGuard` routes too, and they already satisfy it. | `reservations`, `apartments`, `apartment_shots` and `inspections` contracts all already declare `SPECIAL_ACCESS_INVALID`/`SPECIAL_ACCESS_SCOPE_MISMATCH`, all 403. Verified by reading all four. So the extension is additive and cannot go red on the baseline. | APPROVED |
| D11 | A new bind kind `{ kind: "incidentParam"; param: string }` resolves in `targetMatches` by reading `incidents.reservationId` for the incident named by the param and comparing it to `grant.reservationId`. | An incident id is not a reservation id, so neither existing param bind fits. The grant already carries `reservationId`, and `incidents.reservationId` is a direct column, so the check is one lookup — the same narrowing `resolveSubjectApartment`'s incident branch performs at mint time. | APPROVED |
| D12 | Rejected alternative for D11: binding the incident reads by `apartmentParam` (the grant's apartment would match). | The handlers assert **apartment** ownership, not incident identity, so an apartment-wide bind would let a link scoped to one reservation open a claim for a **different stay in the same apartment**. `targetMatches` exists precisely to prevent that narrowing loss. | APPROVED |
| D13 | `GET /assets/apartment/{apartmentId}` reuses the existing `apartmentParam` bind. Only the incident read needs `incidentParam`. | It is apartment-scoped by construction, so its own param is the grant's apartment. Adding a second bind kind for a route that does not need one would be a second thing to get wrong. | APPROVED |
| D14 | The `damage_evidence` scope is **not** added to any `/incidents` route. | It is already served by the unauthenticated `/field/ingest/{token}` surface, which `getFieldContext` resolves through `special_access.incidentItemId`. Adding it to `/incidents` would be a second mechanism for a capability that already works (details-file B6). | APPROVED |
| D15 | For `POST /apartments/{id}/photos/upload-tokens` and `POST /apartments/{id}/photos/confirm`: replace `[authGuard, rolesGuard(["admin","host"]), apartmentGuard(false)]` with `specialAccessGuard({ scope: "inspection_proof", bind: { kind: "apartmentParam", param: "id" }, roles: ["admin","host"] })` **and add an apartment-ownership check in the handler**. | **Correction to the details doc.** The doc says the swap is "the mechanical change; the guard then sets `user` to the owner and the existing handler code works unchanged". That is wrong: `specialAccessGuard`'s session branch calls `authGuard` + `rolesGuard` only — it does **not** call `apartmentGuard`, and neither handler asserts ownership. The swap alone would let any signed-in host mint upload tokens and confirm photos for **any** apartment: a privilege widening on the exact routes being changed. The handler check is `assertApartmentOwnership(db, id, { userId: user.id, role: user.role, allowAdmin: true })`, the repo's own precedent (`incidents.route.ts`, `reservations.route.ts`). On the token path it passes because the guard sets `user` to the apartment's owner — which is also what makes `apartmentGuard` and the token path equivalent. | APPROVED |
| D16 | The ownership check added by D15 is `allowAdmin: true` when no token is present, and **skipped** when `?accessId=` is present. | `apartmentGuard(false)` passed `adminAllowed = false`, so today an admin without ownership is refused; `assertApartmentOwnership` defaults to `allowAdmin = true` and would widen that. Keeping the session path at `allowAdmin: !token` reproduces today's rule exactly. Skipping it on the token path is safe and necessary: the guard already proved the grant's apartment equals the path param and set `user` to that apartment's owner. | APPROVED |
| D17 | `PATCH /reservations/{id}` accepts `?accessId=`, and a **token request is validated against a narrowed schema** — `{ hasPhotoProof?, status? }` only. A session request keeps today's full `UpdateReservationSchema`. | Operator asked for this route; the details doc recommends against it for a real reason: `UpdateReservationSchema` is `CreateReservationSchema.partial()`, so a token holder could move `checkInDatetime`/`checkOutDatetime` — a wider capability than "submit the proofs", and one that can collide with other stays via `assertNoOverlappingReservation`. The narrowed schema gives the guide's submit chain its final call (which sends exactly `hasPhotoProof` and `status: "COVERED"`) while keeping date moves host-only. Same either-or shape as the guard: the narrowed rule applies only when a token is present. | APPROVED |
| D18 | The narrowed PATCH rule is enforced in the **handler** (after `c.req.query("accessId")`), not by a second route or a discriminated contract. | A second `createRoute` for the same method+path is not expressible in Hono/OpenAPI without a variant, and would double the route count for one field rule. The handler reads the query itself — the pattern the guard already uses — and throws `VALIDATION_ERROR` naming the offending fields (the envelope's `details[]` shape), so the failure is a 400 the contract already declares. | APPROVED |
| D19 | The two incident **writes** (`upload-tokens`, `evidence`) also take the `incidentParam` bind and `inspection_proof` scope. | Use case 2 in `special-access-check.md`: the link-holder "is able to post the photos from both pages". Page 1 is the proofs page, so its writes must open, not only its reads. This is wider than the blockers doc's B5, which named only the apartments photo chain — the code-level reason is unchanged: it is the same guard swap plus the bind D11 adds. | APPROVED |
| D20 | `POST /incidents/{id}/items/{itemId}/upload-tokens` and `.../evidence` keep `resolveEditableIncident`, so a **filed** claim still refuses a token with 409 `INCIDENT_NOT_EDITABLE`. | The claim's contents must not move under the guest who is reviewing it — the same rule the host is held to. No change to the mutate gate; only the guard and the param/error contract change. | APPROVED |
| D21 | `GET /special-access/{accessId}` is **anonymous**, and its response is a new narrower schema `SpecialAccessIntrospection` = `{ scope, apartmentId, reservationId, incidentItemId, expiresAt }`. | The `accessId` is the caller's own credential, so echoing it is not a leak; the row `id`, `revokedAt`, `usedAt` and `createdAt` are internal or management data with no use to a link-holder, so the narrower schema omits them. Anonymous is what lets a frontend route guard validate before render without a session — the whole point (B7). | APPROVED |
| D22 | Introspection resolves through `specialAccessService.resolveByToken` (the redemption lookup), not `findByToken` (the management lookup). | `resolveByToken` collapses unknown, expired and revoked to `null`, so all three become one 403 `SPECIAL_ACCESS_INVALID` and the route is not an existence oracle. `findByToken` returns revoked grants — correct for revoke idempotency, wrong here. `usedAt` is deliberately **not** filtered: a spent `damage_evidence` link is still a spent single-use credential, and filtering it is a later decision, not this one. A spent link therefore introspects 200 until the `usedAt` rule is decided — recorded in D23. | APPROVED |
| D23 | A spent (`usedAt` set) `damage_evidence` grant answers **200** from introspection, reporting `scope: "damage_evidence"`. | `resolveByToken` does not filter `usedAt` and `getFieldContext` does. Making introspection agree with `getFieldContext` would mean a second lookup and a second definition of "live". The frontend only ever introspects `inspection_proof` links (it never offers the other scope), so this is unobservable today; recording it here is what stops an executor from "fixing" it mid-flight. | APPROVED |
| D24 | `GET /special-access?reservationId=…` is bearer-only (`authGuard` + `rolesGuard(["admin","host"])`), ownership asserted in the handler against the **grant's** apartment via `assertApartmentOwnership`. | Copying `revokeSpecialAccessRoute`'s existing pattern is what keeps a host from listing another host's links. `reservationId` is required (not optional) in this phase — an apartment-wide list is not asked for and would need its own ownership resolution. | APPROVED |
| D25 | The list response carries `accessId`, and includes **revoked** grants with `revokedAt` populated. | The frontend cannot rebuild the shareable URL without `accessId`, which is the entire point of the list (a host reloads and wants the link back). It is a safe relaxation only because the route is host-authorized against the grant's own apartment. Revoked grants are included because the host needs to see that a link is dead, not have it silently vanish. Both halves are stated in the contract comment so the next reader does not "fix" the `accessId` back out. | APPROVED |
| D26 | The list reuses `SpecialAccessSchema` (which already has every field) and adds `SpecialAccessListSchema = z.array(SpecialAccessSchema).openapi("SpecialAccessList")`. | `SpecialAccess` is already registered in the document, so an anonymous array would inline with no component name; naming the array makes it reviewable in Swagger. No new field is needed, so a second full schema would be a copy that can drift. | APPROVED |
| D27 | `CreateSpecialAccess`'s per-scope rule is documented in the schema's `.openapi({ description })`. It is **not** reworked into a discriminated union. | The rule is already enforced at runtime by `superRefine` (a `400 VALIDATION_ERROR`), and `superRefine` cannot be expressed in JSON Schema. The description-only fix makes the contract tell the truth; a discriminated union changes the generated type shape and every frontend `CreateSpecialAccess` call site for no client-side validator that anyone has asked for. | APPROVED |
| D28 | The introspection and list routes live in `special_access.route.ts` + `special_access.contract.ts`; the introspection schema lives in `special_access.schema.ts`. | They are routes on the same resource with the same ownership and error vocabulary. A second module for two routes would duplicate `assertApartmentOwnership` wiring and the service import. | APPROVED |
| D29 | `GET /special-access/{accessId}` sits in the same file as `DELETE /special-access/{accessId}`; the existing route-ordering comment is checked, not assumed. | Same path, different method, which Hono dispatches on — but the file already carries an ordering comment for exactly this hazard, so the executor verifies it rather than trusting the reasoning. | APPROVED |
| D30 | Every phase ends with a test step whose `Do` is the actual test code, and every phase's `Verify` is `npm run gate`. Phase 1's acceptance is additionally the probe pair. | Tests are never deferred to review (skill Stage 5; this repo's post-mortem). `npm run gate` is the single acceptance command the repo already defines. | APPROVED |
| D31 | Test placement: guard-level behaviour in `src/middleware/specialAccessGuard.test.ts`; route behaviour in each module's existing `*.test.ts`; the two new routes in `special_access.test.ts`; the checker change in `scripts/check-contracts.ts` verified by running it, not by a unit test. | Matches this repo's existing layout exactly (`reservations.test.ts`, `incidents.test.ts`, `apartments.test.ts` all exist and already mock the guard's collaborators). | APPROVED |
| D32 | Six phases, one commit per phase at the phase boundary, docs committed separately from code. | `.husky/pre-commit` runs the whole suite, so per-step commits would pay for 783 tests per step. The migrations/deploy phase touches no `src/`, so it cannot break the suite and can commit on its own. | APPROVED |
| D33 | The three corrections to `backend-blockers*.md` (D14/D12 on `damage_evidence`, D15 on the guard swap, D9 on the checker) are recorded in `00-index.md` and the phase files, **not** by editing the blockers docs. | Those files are the frontend's record of what was believed on 2026-11-25/26 and are quoted as the plan's sources. Rewriting them would destroy the audit trail that shows why the plan diverges from them. | APPROVED |
| D34 | `npm run gate:openapi` is added as the `Verify` for the two phases that change the document shape (B1's scheme/param phase and the new-routes phase); every other phase uses `npm run gate`. | `gate` alone does not build the OpenAPI document, so a scheme registration that renders invalid would pass every other check. This is the one place a narrower/wider verify is genuinely needed rather than copy-pasted. | APPROVED |

## Corrections to the source docs (do not act on these without reading the row)

These are places where the plan deliberately does **not** do what
`backend-blockers-details.md` says. Each is a verified code fact, not a preference.

| # | The details doc says | What the code shows | Decision |
| --- | --- | --- | --- |
| 1 | "Swapping `[authGuard, rolesGuard, apartmentGuard(false)]` for `specialAccessGuard(...)` is the mechanical change; the guard then sets `user` to the owner and the existing handler code works unchanged." | `specialAccessGuard`'s session branch calls `authGuard` + `rolesGuard` **only**. It never calls `apartmentGuard`, and neither photo handler asserts ownership (`apartments.route.ts` relies entirely on the guard for it). The swap alone would let any signed-in host mint tokens and confirm photos for any apartment. | D15 — add the handler-level ownership check. |
| 2 | (implied by the swap) the checker keeps enforcing the contract | `check-contracts.ts` finds guards **by name**: `["authGuard", "rolesGuard", "apartmentGuard"]`. Replacing them with `specialAccessGuard` makes it stop requiring 401 **and** 403 on those routes. | D9 — extend the checker in the same phase. |

(B4) | Correct as far as it goes, but it under-states the work: `GET /incidents/{id}` is **not** the only read the proofs page makes. `resolveOwnedIncident` resolves the claim, then its reservation, then asserts apartment ownership — which the token path satisfies through the impersonated owner. So the guard plus one bind kind really is sufficient, and no handler change is needed for the two incident **reads**. The **writes** additionally keep the `INCIDENT_NOT_EDITABLE` gate (D20). | D11, D19, D20 |
| 4 | "`POST /apartments/{id}/photos/*` ... `apartmentGuard(false)` ... the same shape `specialAccessGuard` reproduces by impersonating the owner." | Same gap as #1: impersonation reproduces the *token* path's ownership, but the session path loses the guard. | D15, D16 |

## Checklist — close every one of these before approval

**Shape**
- [x] Route paths and methods — no existing path/method changes; two new routes (D21, D24)
- [x] Success statuses — `200` for both new routes, `201` for the incident evidence attach (unchanged), `200` for the photo chain (unchanged)
- [x] Request schema strictness — token `PATCH` narrowed to `{hasPhotoProof?, status?}` (D17); `accessId` optional everywhere (D6)
- [x] Pagination / filtering — the list takes a required `reservationId`; no pagination (D24)

**Auth**
- [x] Which guards run, in which order — `specialAccessGuard` replaces the session stack on the six write/read routes (D15, D19); new routes per D21 (none) and D24 (`authGuard`, `rolesGuard`)
- [x] Every role that may call each — `admin`, `host` for every authenticated route; `guest` stays 403 except on the anonymous introspection (D21)
- [x] No signed-in caller gains capability — D15/D16/D17 reproduce today's rules on the session path exactly
- [x] Deliberately unauthenticated — `GET /special-access/{accessId}` (D21), for the same reason `/field/ingest` is

**Failure modes**
- [x] Registry code for each — no new codes; all of `SPECIAL_ACCESS_INVALID`, `SPECIAL_ACCESS_SCOPE_MISMATCH`, `VALIDATION_ERROR`, `RESERVATION_NOT_FOUND` already exist in `ERROR_REGISTRY`
- [x] Status for each, confirmed against the registry — 403, 403, 400, 404
- [x] 400 vs 403 vs 409 split — a bad token is 403 (never 401, never a fallback); a token sending a non-photo-proof PATCH field is 400; a filed claim is 409
- [x] Which errors expose an id or driver text — none; the introspection body is narrowing-only, messages name nothing

**Data**
- [x] Schema change — none (D4, spec §Data changes)
- [x] Migration — none added; `0015`/`0016` are applied to production as ops (D2)
- [x] Foreign keys — unchanged
- [x] Unique constraints / SQLSTATEs a client can trip — the only constraint in play is `special_access_access_id_unique`, which `create` already respects

**Breaking changes**
- [x] Existing response shape changed — no
- [x] Existing status code changed — no. On the changed routes the *token* path gains 403s it should always have produced (B3), and the session path is unchanged (D16)
- [x] Client action required — yes: `covera` must re-run `npm run api:generate` then `npm run gate`, which Phase 5 documents

**Process**
- [x] Six phases, one commit each, docs separate (D32)
- [x] Every phase ends in a test step with real test code (D30)
- [x] Every Accept is a command or a grep with a stated result (skill Stage 5)
- [x] `npm run gate` green on the baseline — verified 2026-11-26, 783 tests, 49 routes
